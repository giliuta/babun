# Редактор услуги — окончательный дизайн (2026-08-21)

Решение по ТЗ владельца от 2026-08-21 («сделай полноценную под каждую: кол-во, цена за одну…
короче делай ещё расход колонку… вызови дизайнера»). Собрано из пяти проектов и трёх судейств.
Всё, что ниже, — утверждение с доводом. Спорное вынесено в §11 тремя вопросами.

СТАВКА ОДНОЙ ФРАЗОЙ: таблица остаётся ПЛИТАМИ (закон 2026-08-21), но их становится ЧЕТЫРЕ;
первая строка перестаёт быть серой «1» и становится чёрным «от 1»; знак валюты стоит в каждой
денежной клетке; шапка колонок ЛИПНЕТ к верху прокрутки; над клавиатурой появляется полоса
«Далее / Готово». Дни доступности рисуем ВМЕСТЕ с читателем, онлайн-запись не рисуем вовсе.

ИСХОДНАЯ ФАКТУРА (проверено по коду, а не по памяти):
* `ServiceRows.tsx`: `Block` НЕ ИМЕЕТ `paddingHorizontal`; `GAP = 8`, `QTY_W 104 + MONEY_W 128 +
  TIME_W 122 = 354`, плюс два зазора = 370. Внутренние поля плит СЕГОДНЯ РАВНЫ НУЛЮ — все пять
  проектов вычитали поля, которых нет, и на этом фантоме роняли кегли и резали слова.
* `CellInput.tsx`: `fontSize 16`, `height 56`, `paddingHorizontal 0`, `maxFontSizeMultiplier`
  ОТСУТСТВУЕТ ВООБЩЕ. Ячейка времени рядом печатается 17pt, частица «от» — 15pt, подписи — 12pt.
  Четыре кегля в одной таблице — не система, а осадок.
* `format.ts`: `durationLabel` — ОДИН формат на четыре поверхности, заведён 2026-08-17 именно
  чтобы услуга не звучала двумя способами. Второго формата не будет.
* `economics.ts`: `parsePriceTiers` ВЫБРАСЫВАЕТ строку без валидной цены — класть расход внутрь
  `price_tiers` нельзя, строка «только расход» исчезла бы при первом чтении.
* `packages/shared/src/local/services.ts`: `pricePerUnit` — последняя строка с `min_qty ≤ qty`;
  `durationForQuantity` — якоря + продолжение наклоном; `getServiceMaterialCost` читает
  `cost_per_unit` (сегодня 0 у всех, писателя в мобильном нет).
* `master-reference.ts`: оба маппера принудительно ставят `cost_per_unit: 0`; у мастера
  `price_tiers: null`, у диспетчера `price_tiers` проходит, `available_weekdays` затирается в `[]`.

## 1. Лист целиком

Нижний лист `BottomSheet`, `maxHeightRatio 0.9`, прокрутка, футер вне прокрутки.
Шапка: «Новая услуга» (создание) / «Услуга» (правка); справа мусорка — только у правки.

### 1.1 Пустая услуга (создание)

```
———— грабер ————
Новая услуга

Название — как в счёте
[ ● |                                   ]

＋ Описание

 Кол-во   Цена за одну   Расход за одну   Время на всё      ← ЛИПНЕТ при прокрутке
┌──────┐ ┌────────────┐ ┌──────────────┐ ┌──────────────┐
│ от 1 │ │ €          │ │ €0           │ │ 1 ч          │
└──────┘ └────────────┘ └──────────────┘ └──────────────┘

＋ Добавить          ＋ Дни, когда доступна

                    [  Создать  ]
```
Цена приезжает ПУСТОЙ (пусто ≠ ноль — закон, оплаченный бесплатной услугой в счёте), расход —
напечатанным «€0», время — «1 ч» (сегодняшний засев 60 минут). Ошибок нет, пока не нажали
«Создать».

### 1.2 Услуга с тремя количествами

```
Название — как в счёте
[ ● | Мойка фасада                      ]

＋ Описание

 Кол-во   Цена за одну   Расход за одну   Время на всё
┌──────┐ ┌────────────┐ ┌──────────────┐ ┌──────────────┐
│ от 1 │ │ €       50 │ │ €         10 │ │   1 ч 30 мин │
│ от 3 │ │ €       45 │ │ €         10 │ │        4 ч   │
│ от 7 │ │ €       40 │ │ €          8 │ │   8 ч 30 мин │
└──────┘ └────────────┘ └──────────────┘ └──────────────┘

＋ Добавить          ＋ Дни, когда доступна

                    [ Сохранить ]
```
Тап по ячейке времени: клавиатура уходит первой, барабан ЧЧ:ММ раскрывается ПОД всеми четырьмя
плитами во всю ширину 370 (внутри 94-й плиты пара колонок не помещается физически, а рост одной
плиты развалил бы выравнивание строк между блоками — это уже разобрано в коде и не пересматривается).
Строку убирают долгим нажатием + системный Alert «Убрать «от 3»?» с телом `tierSentence`:
«от 3 — по €45 · 4 ч на всё», кнопки «Отмена» / «Убрать». Свайпа у разрезанной строки нет и не будет.

### 1.3 Услуга со всем заполненным

```
Название — как в счёте
[ ● | Мойка фасада                      ]

Описание в счёте
[ Мойка фасада с люльки, до 12 метров,   ]
[ с реагентом. Стекло входит.            ]
[                                        ]

 Кол-во   Цена за одну   Расход за одну   Время на всё
┌──────┐ ┌────────────┐ ┌──────────────┐ ┌──────────────┐
│ от 1 │ │ €       50 │ │ €         10 │ │   1 ч 30 мин │
│ от 3 │ │ €       45 │ │ €         10 │ │        4 ч   │
│ от 7 │ │ €       40 │ │ €          8 │ │   8 ч 30 мин │
└──────┘ └────────────┘ └──────────────┘ └──────────────┘
        ← раскрытая строка: барабан ЧЧ:ММ во всю ширину, 144pt

＋ Добавить

Дни, когда доступна
[Пн][Вт][Ср][Чт][Пт][Сб][Вс]      ← погашенные Сб и Вс = t.fill/faint

Впишите цену                       ← красная строка, ТОЛЬКО когда есть ошибка

                    [ Сохранить ]
```
Над клавиатурой — полоса `InputAccessoryView`: слева «Далее» (следующая правимая клетка по
строкам), справа «Готово» (убирает клавиатуру). Это контрол, а не подсказка: у `decimal-pad` нет
ни Return, ни «Готово», и без полосы двенадцать клеток обходятся только прицельным тапом.

Тост после сохранения: обычно «Услуга сохранена»; если правили СУЩЕСТВУЮЩУЮ услугу и расход
изменился — «Расход учтён и в прошлых записях» (см. §5).

Слов, которых на листе нет: «Дополнительно», «порог», «ступень», «опт», «тариф», «единица
измерения», «себестоимость», «маржа», «например», «шт». Подсказок в полях нет. Объясняющих
абзацев нет. Тихой строки-предпросмотра «а что будет на семи» нет.

## 2. Геометрия

Коэффициенты (SF Pro Text, с запасом в бо́льшую сторону): цифра tabular 0,60 × кегль ·
кириллическая строчная 0,55 · пробел 0,28 · «€» 0,58 · запятая 0,27.
При 16pt: цифра 9,6 · буква 8,8 · пробел 4,48 · € 9,28 · запятая 4,32.
При 15pt: буква 8,25 · пробел 4,2. При 12pt: буква 6,6 · пробел 3,36.

Доска: 402 − 2×16 (гуттер листа) = **370pt**. Три зазора по 8 = 24 → **346pt на четыре плиты**.
Внутреннее поле плиты ВВОДИТСЯ ЯВНО: `paddingHorizontal: 4` (сегодня 0). Четыре точки — это не
декорация, а расстояние от каретки до кромки заливки; без него курсор целуется с краем.

| Колонка | Ширина | Содержимое (W−8) | Худшее значение | Занимает | Запас |
|---|---|---|---|---|---|
| Кол-во | 64 | 56 | «от 128» = 16,5+4,2+3×9,6 + каретка 6 | 55,5 | +0,5 |
| Цена за одну | 90 | 82 | «€1 250,50» = 9,28+3+6×9,6+4,48+4,32 | 78,7 | +3,3 |
| Расход за одну | 90 | 82 | то же | 78,7 | +3,3 |
| Время на всё | 102 | 94 | «23 ч 55 мин» = 4×9,6+4×8,8+3×4,48 | 87,0 | +7,0 |
| **Сумма** | **346** | | | | +24 зазора = **370** ✓ |

Типичные значения дышат: «от 3» ≈ 36 в 56 · «€50» = 9,28+3+19,2 = 31,5 в 82 ·
«1 ч 30 мин» = 77,4 в 94.

**Две денежные колонки одинаковой ширины до пикселя (90 и 90) — закон.** Разный правый край у
соседних денежных столбцов убивает вычитание глазом, а это единственная причина, по которой
расход просили поставить РЯДОМ с ценой, а не спрятать.

**Подписи, 12/500, `numberOfLines 2`, блок фиксированной высоты 30pt** (чтобы четыре шапки стояли
на одной базовой линии независимо от переноса):
«Кол-во» 39,6 ≤ 64 · «Цена за одну» 72,7 ≤ 90 · «Расход за одну» 85,9 ≤ 90 · «Время на всё»
72,7 ≤ 102 — при обычном кегле все ОДНОСТРОЧНЫЕ, перенос не наступает. При ×1,2 «Расход за одну»
= 103 > 90 и переносится по пробелу; самый длинный токен «Расход» = 47,5 ≤ 90 ✓. Шапка не
клипается и не переписывает себя — она складывается.

**ТРИ КЕГЛЯ НА ЛИСТ** (закон ДС, сегодня нарушен): 12/500 — подписи колонок; 15/400 — частицы
«от» и знак валюты, накладки «＋ …», ярлыки полей; 16/400 — ВСЕ значения и все вводы. Ячейка
времени падает с 17 на 16 — это не плата за четвёртую колонку, а починка разнобоя.

**Dynamic Type.** `maxFontSizeMultiplier={1.2}` ставится ЕДИНООБРАЗНО на все ячейки и подписи
(у `CellInput` его сегодня нет вообще — цена клипается при крупном шрифте уже сейчас, до всякой
четвёртой колонки). При ×1,2 держатся: «от 12» (44,6 ≤ 56), «€12 500» (77,8 ≤ 82), «8 ч 30 мин»
(92,9 ≤ 94). НЕ держатся два случая, и я называю их прямо, а не прячу: «€1 250,50» (94,4 > 82) и
двузначные часы «11 ч 45 мин» (104,4 > 94). Оба живут в TextInput/Text, которым ставится
`adjustsFontSizeToFit` с `minimumFontScale 0.9`; при фокусе поле само прокручивает содержимое.
Копеек в прайсе выездного сервиса нет ни у одного из шести живых прайсов, услуги длиннее десяти
часов — тоже; это допущение, а не доказательство.

**Цели касания.** Самая узкая клетка 64 × 56 ≥ 44×44 ✓. День недели: (370 − 6×6)/7 = 47,7 × 44 ✓.

**Вертикаль.** Подписи 30 + строки по 56 + волосяные разделители. Три количества = 30 + 170 = 200.
Барабан 144 + 8. Лист 0,9 × 874 = 786; шапка 56, футер 68, клавиатура `decimal-pad` ≈ 291 →
на прокручиваемое тело ≈ 371pt: имя 72 + «＋ Описание» 27 + таблица 200 + «＋ Добавить» 33 = 332 ✓.

**ЛИПКАЯ ШАПКА — ОБЯЗАТЕЛЬНА, А НЕ УКРАШЕНИЕ.** С пятой строки, чтобы печатать в неё под поднятой
клавиатурой, надо прокрутить 30 + 4×56 = 254pt при окне ≈ 371 — шапка уезжает ровно тогда, когда
четыре голых числа надо различить. Строка подписей становится прямым ребёнком прокрутки листа и
получает `stickyHeaderIndices` (слова `stickyHeaderIndices` в `apps/mobile/src` сегодня нет ни
разу). Плюс дописывается мёртвый `rowTops` (объявлен в `services.tsx`, читателей ноль): `onLayout`
строки → `scrollTo` при `onFocus`, чтобы сфокусированная строка выходила из-под клавиатуры.

**ПЯТОЙ КОЛОНКИ НЕ БУДЕТ — это конструктивный потолок, а не вкус.** 346/5 = 69,2pt на плиту при
подписи «Цена за одну» = 72,7 — не влезает УЖЕ при обычном кегле. Следующее расширение обязано
ломать структуру («строка = количество + своя страница»), а не подрезать поля.

## 3. Первая строка

**Было:** «1», `t.faint`, нередактируемая. **Стало:** «от 1» — частица «от» 15/400 `t.faint`
(как во всех строках), число 16/400 **`t.ink`**, tabular. Не поле, без рамки, без подсветки нажатия.

Три довода, ни одного про вкус:
1. Владельцу не понравилась не единица, а СЕРЫЙ. В этом продукте серым печатают выключенное и
   несуществующий ноль. Серая «1» посреди чёрных цен сообщала «эта строка не работает» — про
   единственную строку, которая работает всегда и чья цена уезжает в 100% счетов.
2. Одна грамматика на колонку. «1 · от 3 · от 7» — два языка в одном столбце; «от 1 · от 3 · от 7»
   — одна лестница, читаемая вслух.
3. Это правда о механике: `pricePerUnit` держит базовую цену, пока не встретит строку с
   `min_qty ≤ qty`; при строках «от 3» и «от 7» база работает на 1 и 2 — она и есть «от 1».
   И то же слово бесплатно закрывает §7.

Нередактируемость показана МАТЕРИАЛОМ, а не пигментом: правимая клетка при фокусе получает белую
подложку `t.surface` на плите `t.fill` (тот же приём, которым сегодня помечена раскрытая ячейка
времени, распространённый на все поля). «от 1» не белеет никогда, потому что тапать в ней нечего.
Тап по «от 1» не мёртвый — он ставит курсор в цену ЭТОЙ ЖЕ строки: мёртвых зон 64×56 на iPhone быть
не должно. Долгое нажатие не делает ничего: определение убрать нельзя. Цена, расход и время первой
строки правятся как у всех — это колонки самой услуги (`price`, `cost_per_unit`, `duration_minutes`).
Ярлык ротора: «От 1, всегда».

Чего не будет: замка, слов «базовая», «стандарт», «одна услуга», «шт» (единица измерения снесена
2026-08-21 и возврату не подлежит), «Одна» словом (колонка называется «Кол-во», в ней стоит число).

## 4. Евро в каждой строке

Из подписи «, €» УХОДИТ («Цена за одну», «Расход за одну») — единицу дважды не пишут.

Анатомия денежной клетки (90 × 56):
```
[4 поле][ Text «€» 15/400 t.faint, pointerEvents none, accessible false ][ TextInput flex:1,
          textAlign "right", 16/400, t.ink, tabular-nums, decimal-pad, selectTextOnFocus ][4 поле]
```
* **Знак — отдельный `Text`, а не часть `value`.** Внутри `TextInput` он ломает ввод трижды:
  попадает под `selectTextOnFocus` и стирается первой цифрой; `decimal-pad` не умеет напечатать
  его обратно; `Number("€50")` = NaN, и цена молча уезжает нулём. Снаружи он не мешает вовсе:
  палец в него не попадает, курсор его не видит, парсер о нём не знает.
* **`accessible={false}`** на символе — иначе VoiceOver делает отдельную остановку на «€» перед
  каждым полем: четыре колонки × N строк лишних остановок.
* **Знак прижат к левой кромке клетки, число выровнено ВПРАВО.** Это буква закона ДС («числовые
  колонки — по правому краю»): цифры идут единицами под единицами, а правый край цены стоит ровно
  напротив правого края расхода — вычитание делается взглядом. Между знаком и числом остаётся
  переменная дыра — так печатает любая банковская выписка, и поскольку обе денежные плиты одной
  ширины (90 и 90), дыра никогда не сдвигает вертикальное чтение.
* **Символ берётся из валюты тенанта** — `moneySymbol(currency)` (`packages/shared/src/common/
  utils/money.ts`), а не литералом. Сегодняшняя подпись «Цена за одну, €» — единственное место в
  продукте, где евро прибито гвоздём, и у гривневого тенанта это прямая ложь. Владелец получит «€»,
  потому что его тенант в EUR.
* **Знак стоит всегда, даже в пустой клетке.** Пустая цена показывает одинокий «€» — это и есть
  подсказка без единого слова (подсказок в полях по закону нет).
* Ноль расхода печатается «€0», где число — `t.muted`, знак остаётся `t.faint`: «ноль тише живых
  денег». Так «стандарт — ноль» ВИДНО.
* Минуса перед расходом нет: это норматив, а не операция; минус у «Расхода» из продукта уже убирали.
* Грамматика чисел — из `money.ts`: символ перед числом, неразрывный пробел разрядов, запятая
  десятичная, копейки только когда они есть.
* Ротор читает клетку одной фразой: «Цена за одну, 45 евро».

## 5. Расход

**ЧТО ВВОДЯТ.** Расход НА ОДНУ ШТУКУ, в валюте тенанта, `decimal-pad`, ≥ 0. Подпись «Расход за
одну» намеренно зеркалит «Цена за одну» и намеренно противопоставлена «Время на всё»: две колонки
— за единицу, одна — на всю строку. Это единственная асимметрия таблицы, поэтому она названа
словом, а не оставлена на догадку.

**ПО УМОЛЧАНИЮ — НОЛЬ, НАПЕЧАТАННЫЙ.** Первая строка новой услуги: «€0» цветом `t.muted`. Клетка
расхода пустой не бывает никогда: очищенная, на `blur` она видимо схлопывается в «€0». У цены
пусто ≠ ноль (закон, оплаченный бесплатной услугой в счёте), у расхода можно наоборот — и критерий
тот же самый: расход НЕ ДОХОДИТ ДО КЛИЕНТА, он живёт только в прибыли.

**НОВАЯ СТРОКА НАСЛЕДУЕТ РАСХОД СТРОКИ ВЫШЕ** (цена по-прежнему приезжает пустой, время —
засеянным умножением, как сегодня). Довод: цена от количества почти всегда ниже базовой, поэтому
подставлять её нельзя («оно меняет цену всегда на 50 — мне это не нравится»), а расход материалов
на единицу от количества не падает — та же химия на ту же штуку. Угадывать нечего, значит
подставлять можно. Пока у всех ноль, наследование и есть ноль.

**КАК СЧИТАЕТСЯ НА КОЛИЧЕСТВЕ.** Расход — ступенька, как цена, а НЕ прямая, как время: действует
расход последней строки с `min_qty ≤ qty`, и он умножается на количество. Это дословно разрешает
колебание владельца: «выставил расход 10 — на двух получится 20» (умножает КОЛИЧЕСТВО, а не
величина удваивает себя); «добавляет ещё» — заводит строку «от 3» со своим числом, и с трёх
работает она. Автоматического удвоения самой величины (10 → 20 в клетке) не будет ни на экране, ни
в базе: справочник хранит цену одной штуки, умножает запись. Интерполяции у расхода нет — наклон
между строками сочинял бы цифру, которую человек не вводил.

**ФОРМА ХРАНЕНИЯ.**
* Первая строка → существующая `services.cost_per_unit` (`numeric`, `default 0`, уже читается
  `getServiceMaterialCost` → `appointmentMaterialCostLines`). В мобильном у неё сегодня нет
  писателя — он появляется.
* Строки от количества → НОВАЯ `services.cost_tiers jsonb not null default '[]'::jsonb`,
  элемент `{min_qty: int ≥ 2, cost_per_unit: number ≥ 0}`, сортировка по `min_qty`, дубли
  схлопываются последним — зеркало `price_tiers`/`duration_tiers` до буквы.
* **Почему не внутрь `price_tiers`,** хотя это дешевле на миграцию: (1) `parsePriceTiers`
  выбрасывает элемент без валидной цены — строка «выставил только расход» исчезла бы при первом
  же чтении вместе с деньгами; (2) `price_tiers` ОТДАЁТСЯ проекции диспетчера, которая специально
  затирает `cost_per_unit: 0`, — положив расход туда, мы отправили бы маржу владельца каждому
  диспетчеру через ту самую проекцию, которая её прячет; (3) колонка с именем «цены», хранящая
  себестоимость, — ложь в схеме («у сущности одно имя»).

**ВЛИЯНИЕ НА ПРИБЫЛЬ ЗАПИСИ.** Расход строки записи = `costPerUnit(service, qty) × qty`. Новый
резолвер `costPerUnit(service, qty)` кладётся в `packages/shared/src/local/services.ts` рядом с
`pricePerUnit` (тот же алгоритм), `getServiceMaterialCost` становится его частным случаем при
qty = 1, и `appointmentMaterialCostLines` начинает передавать количество, которое у него уже есть.

**ВЛИЯНИЕ НА УЖЕ ОТКРЫТЫЕ И ЗАКРЫТЫЕ ЗАПИСИ — НАЗЫВАЮ ЧЕСТНО.** Снимок `appointments.services[]`
не меняется ни на байт: расход в него не пишется, `buildServices` не трогается, триггер
`protect_paid_appointment_finance` не тревожится — оплаченные записи неприкосновенны. НО расход
читается из ЖИВОГО каталога (количество из снимка, `unitCost` из текущей услуги), поэтому первое
же ненулевое число немедленно уменьшит показанную прибыль ВСЕХ прошлых записей с этой услугой —
в «Финансах», в сводке дня и в разборе прибыли. Это поведение существует СЕГОДНЯ у `cost_per_unit`
и не создаётся лестницей; новым становится лишь то, что до сих пор им нельзя было воспользоваться.
Плата — одна фраза в тосте ровно в момент возникновения риска: **«Расход учтён и в прошлых
записях»** (только при правке существующей услуги и только если расход изменился). Не абзац под
карточкой, не новая сущность, не «дата действия расхода». Заморозка (расход в снимок записи) —
отдельное решение о деньгах: новое поле в `services[]` изменит байты при первой пересборке и
сломает сохранение открытой оплаченной записи. См. §11, вопрос 1.

**ГДЕ РАСХОД НЕ ДОЛЖЕН ПОЯВИТЬСЯ.** `cost_tiers` не попадает ни в `list_master_services_safe`,
ни в `list_dispatcher_services_safe`, а оба маппера в `master-reference.ts` получают
`cost_tiers: null` в ту же пару строк, где уже стоит `cost_per_unit: 0`. Проекция и её маппер —
одна пара; тест в `master-reference.test.ts` дописывается тем же движением.

а не имя вещи; постоянный раздел с остатками — это ровно та панель «ЦЕНА ЗА», которую владелец

### 6.1 Онлайн-запись — НЕ РИСУЕМ. Говорю прямо, потому что мягко тут нельзя.

Онлайн-записи в продукте нет вообще: ни публичной страницы, ни ссылки для клиента, ни виджета, ни
движка слотов. Колонка `services.online_enabled` существует, стоит `true` у ВСЕХ шести услуг прода,
и её не читает ни одна строка мобильного приложения; единственный чекбокс живёт в операторском
вебе, который подлежит удалению. Тумблер «Онлайн-запись» сегодня — выключатель у лампы, которой
нет в доме: он не доходит до клиента и не двигает ни цента, то есть проваливает ОБА условия
закона, по которому за неделю снесли «имя для клиента», «материалы», единицу измерения, «продаём
целиком» и категории. Хуже: раз `online_enabled = true` уже у всех, в день появления фичи весь
прайс окажется опубликован без единого решения владельца.

Что предлагается вместо тумблера (это ответ на «чтобы было так полезно», а не отказ): онлайн-запись
— не свойство услуги, а продукт компании. Порядок: (1) Кабинет → «Онлайн-запись»: адрес вида
`babun.app/b/<компания>`, включается ОДИН раз на компанию; свободные окна берутся из графика
команды, который уже есть (свои часы у каждой команды с 2026-08-17) и из буфера после записи;
(2) прайс на этой странице и есть список услуг; (3) и только тогда у услуги появляется строка
«Показывать в онлайн-записи» — точнее, страница `ToggleListScreen` «Что можно записать онлайн»
со всеми услугами галками в одной двери (закон «один дизайн на все списки»), а не тумблер,
повторённый внутри каждой из тридцати услуг. Колонку `online_enabled` СЕЙЧАС не трогаем и не
пишем; дропать нельзя — легаси-веб в неё ещё пишет, уйдёт вместе с ним.

### 6.2 Дни доступности — РИСУЕМ, но только в паре с читателем, одним заходом.

`services.available_weekdays jsonb` тоже пуста у всех и тоже без читателей, но, в отличие от
онлайн-записи, читатель существует, мал и настоящий: выбор услуги в записи уже знает дату.
Условие, без которого накладка не рисуется: в этом же заходе делается фильтр в `/book`.

Вид. Накладка «＋ Дни, когда доступна» (15/500, accent) справа от «＋ Добавить». Тап ЗАМЕЩАЕТ её
на месте (второго листа не бывает: `ChoiceSheetHost` физически уходит за `BottomSheet`): ярлык
«Дни, когда доступна» 13/500 и под ним семь клеток — (370 − 6×6)/7 = 47,7 × 44, подпись 13/700,
`WEEKDAY_LABELS` («Пн Вт Ср Чт Пт Сб Вс»), рецепт взят из недельной полосы `TeamScheduleSheet`.
Выбранный день — оттиск (заливка `${t.accent}14`, текст accent), невыбранный — `t.fill`/`t.faint`.

Механика, забранная у проекта 5 целиком:
* **При раскрытии горят ВСЕ СЕМЬ** — это единственное правдивое изображение текущего состояния
  («доступна всегда»). Пустая полоса на входе сказала бы обратное. Действие человека — ГАСИТЬ.
* **Все семь горят = ограничения нет**, в базу уходит `[]`; при следующем открытии блок снова
  свёрнут в накладку. Тот же жизненный цикл, что у описания, — не новый прецедент.
* **Последний день не гаснет.** Тап, который погасил бы седьмой, не делает ничего:
  `haptics.warning` и всё. Ни алерта, ни красной строки. Услуга, недоступная никогда, — это
  удалённая услуга, и у неё уже есть своя дверь (мусорка в шапке).
* Блок убирают долгим нажатием + системный Alert, как строку таблицы.

Читатель в записи:
* Услуга **НЕ ПРЯЧЕТСЯ** — спрятанная читается как пропавшая (урок уже оплачен: удаление из
  бригады молча уносило услугу у всех). Она уезжает ВНИЗ списка, имя `t.muted`, и на месте цены
  печатаются её дни: «Пн Вт Ср Чт Пт».
* Тап разрешён. Системный Alert: «Суббота — не день этой услуги» / «Мойка фасада: Пн Вт Ср Чт Пт»
  / «Отмена» · «Всё равно». Запрета нет, есть предупреждение: диспетчер, которому клиент платит
  за субботу, доводит запись до конца одним тапом.
* **Перенос даты уже собранной записи не делает НИЧЕГО** — ни удаления строки, ни алерта, ни
  пересчёта. Ограничение — фильтр в момент выбора, а не сторож на записи; иначе перенос трогал бы
  строки, которые сервер сравнивает побайтово.
* `available_weekdays` ОБЯЗАН уехать в `list_dispatcher_services_safe` (сегодня маппер затирает
  его в `[]`), иначе ограничение невидимо ровно тому человеку, который записывает клиентов.

## 7. За последней строкой

Механика уже такая, как хочет владелец, — проверено по коду, менять нечего:
* **Цена** за последней строкой замирает на цене последней строки (`pricePerUnit`): «от 7 по 40»
  буквально значит «семь и больше по сорок». Скидка не углубляется сама — иначе на пятнадцати
  штуках услуга уходила бы в ноль без ведома владельца.
* **Расход** ведёт себя как цена (ступенька), потому что это цена материала, а не темп бригады.
* **Время** продолжает РАСТИ наклоном последнего отрезка (`durationForQuantity`): бригада на
  восьмом объекте не телепортируется. Хочешь, чтобы время замерло, — заводишь следующую строку с
  тем же временем, наклон становится нулевым. Тем же контролом, без единой новой настройки.
* **Строк от количества нет вовсе:** цена × количество, время × количество, расход × количество.
  Степпер количества в записи не имеет потолка и не упирается ни во что — «тапаешь и услуга просто
  увеличивается» работает уже сегодня. Ограничения «дальше семи нельзя» нет и не заводим:
  справочник описывает цену, а не разрешение продавать.

**НА ЭКРАНЕ УСЛУГИ НЕ ПИШЕТСЯ НИ СЛОВА.** Тихую строку-проверку владелец забраковал дословно
(«внизу не нужно писать, это полная хуета»). Отвечает грамматика левой колонки — «от 1 · от 3 ·
от 7»: у предлога «от» нет верхней границы, поэтому последняя ступень читается открытой. Именно
ради этого §3 переписывает первую строку: пока там стояла одинокая «1», колонка читалась как
«единица и лестница», и лестница требовала пояснения.

Возражение, которое я принимаю и на которое отвечаю: у строк 1…n−1 «от» закрыто следующей
строкой, а у последней открыто. Одно слово в двух смыслах. Это ровно та же грамматика, которой
человек говорит вслух («от трёх — по сорок пять, а от семи — по сорок»), и она читается верно
только сверху вниз — что колонка и делает. Никакая подпись этого не улучшит, а «от 1 · 3 · 7»
без первого «от» стало бы хуже.

**Где ответ виден глазами — в ЗАПИСИ, а не в справочнике.** Вопрос «что будет на девяти» человек
задаёт, когда крутит количество: строка записи печатает количество, цену за одну и итог, и они
пересчитываются на каждый тап. Правка ДРУГОГО экрана, входящая в этот заход одной строкой:
строка услуги в записи печатает итог «8 × €40» рядом с ценой, чтобы пересчёт был виден без
арифметики в голове.

**И ещё одна честная правка не этого листа:** строка СПИСКА услуг печатает сегодня одну цену
(`formatEURExact(svc.price)`), то есть после лестницы витрина скажет «€50» про услугу, которая с
семи стоит €40. Владелец смотрит на список ПЕРВЫМ. Строка списка при заведённой лестнице печатает
«€50 → €40 · 1 ч 30 мин»: стрелка = «падает до», одна глифа, ни одного нового слова.

## 8. Данные и миграции

| Колонка | Состояние | Что делаем |
|---|---|---|
| `services.price`, `duration_minutes` | есть | первая строка, как сегодня |
| `services.cost_per_unit` `numeric default 0` | есть, читается `getServiceMaterialCost`, писателя нет | РАСХОД ПЕРВОЙ СТРОКИ; появляется писатель |
| `services.cost_tiers` | **НЕТ** | НОВАЯ: `jsonb not null default '[]'::jsonb` |
| `services.price_tiers`, `duration_tiers` | есть | как сегодня; расход в них НЕ кладём |
| `services.bulk_threshold`, `bulk_price` | легаси, читатель жив | продолжают уезжать явными нулями |
| `services.available_weekdays` `jsonb '[]'` | есть, читателей ноль | получает ПЕРВОГО читателя (`/book`) и писателя |
| `services.online_enabled` | есть, `true` у всех, читателей ноль | НЕ ТРОГАЕМ вовсе |

Миграция одна, добавляющая:
```sql
alter table public.services
  add column if not exists cost_tiers jsonb not null default '[]'::jsonb;
comment on column public.services.cost_tiers is
  'Расход за одну от количества: [{"min_qty":3,"cost_per_unit":8}], min_qty>=2, сортировка по min_qty.';
```

Порядок применения:
1. Миграция `cost_tiers` (обратима `drop column`, ломать нечего).
2. `database.types.ts` регенерируется — иначе колонка невидима типам.
3. Резолвер `costPerUnit` в shared + правка `appointmentMaterialCostLines` + тесты — ДО экрана,
   чтобы новая математика существовала до того, как её начнут заполнять.
4. Мапперы ролей и RPC (`cost_tiers` не выбирается и затирается; `available_weekdays` ДОБАВЛЯЕТСЯ
   в проекцию диспетчера) — тем же коммитом, что и SQL.
5. Экран: четвёртая плита, липкая шапка, €-клетка, «от 1», дни, полоса над клавиатурой.
6. Читатель дней в `/book` — в этом же заходе, иначе накладка дней не рисуется (§6.2).

Что со старыми услугами: ничего. `cost_tiers = []` означает «расход не зависит от количества»,
`cost_per_unit = 0` у всех шести услуг прода, `price_tiers`/`duration_tiers` не заполнил никто.
После миграции не меняется ни один цент ни на одном экране — это проверяемое утверждение.

Что со старыми записями: снимок `appointments.services[]` не меняется ни на байт (мина №1 не
срабатывает). Оговорка про живое чтение расхода — §5.

**Мина №3 (частичный патч `useUpdateService`) закрывается явной записью:** `cost_per_unit`
пишется ВСЕГДА, включая явный `0`; `cost_tiers` пишется целиком каждым сохранением, убранные
строки уезжают явным `[]`; `available_weekdays` — явным массивом (пустой = «любой день»).
Молчание здесь воскрешает стёртые деньги — на этом уже обжигались с `bulk_threshold`/`bulk_price`.

## 10. Чего НЕ делаем и почему

1. **Тумблера онлайн-записи** — включать нечего, §6.1.
2. **Второго формата времени** («12 ч 45» вместо «12 ч 45 мин»). `durationLabel` свели в одну
   функцию 2026-08-17 именно потому, что услуга звучала двумя способами в двух тапах друг от
   друга. 32 точки того не стоят, и они нам не нужны: время получает 102pt.
3. **Не схлопываем плиты в одну карточку** — закон «колонка = плита» залочен 2026-08-21 по живой
   боли («в белой карточке читаются строки, а колонку не видно»), и по ширине одна плита дала бы
   всего +8pt. Свайп по строке остаётся невозможным, дублёр — долгое нажатие + Alert.
4. **Не уходим на отдельную страницу лестницы** — это лишний тап и увод цен из места, где владелец
   видит их целиком; он три круга подряд строил именно таблицу.
5. **Не кладём расход в `price_tiers`** — §5, три довода.
6. **Не запекаем расход в снимок записи** — новое поле в `services[]` меняет байты при первой
   пересборке `buildServices` и ломает сохранение открытой оплаченной записи (мина №1).
7. **Не заводим «дату действия расхода»** — вторая сущность ради редкого случая.
8. **Не рисуем пятую колонку и не готовим место под неё** — конструктивный потолок, §2.
9. **Не пишем на экране ничего про «за последней строкой»** — §7.
10. **Не подставляем цену в новую строку** — прямой отказ владельца.
11. **Не прячем услугу, недоступную в этот день** — прячем = «пропала», §6.2.
12. **Не заводим `material_costs` заново** (совместимостный хвост без писателя) и не трогаем
    `bulk_threshold`/`bulk_price` (читатель легаси жив, писатель снят — так и остаётся).

## 11. Вопросы владельцу (три)

**1. Расход в справочнике переписывает прибыль ПРОШЛЫХ месяцев. Оставляем так?**
Расход читается из живой услуги: впишешь сегодня €10 — прибыль за июль перестанет сходиться с
той, что ты видел в июле. Сама запись при этом цела, меняется только цифра в отчёте.
*Рекомендация: оставить так и показывать тост «Расход учтён и в прошлых записях».* Заморозка
(расход в снимок записи) — отдельная правка с миграцией сравнения, делать её попутно нельзя.

**2. Дни доступности: делаем вместе с фильтром в записи в этом же заходе?**
Без читателя это второй `online_enabled`, и тогда накладку не рисуем вовсе — половина фичи хуже
её отсутствия. *Рекомендация: да, делаем — это +1,5 часа: недоступная услуга уезжает вниз списка,
печатает свои дни и спрашивает «Всё равно».* Отдельно скажу: «по воскресеньям не работаем» — это
свойство КОМАНДЫ, и оно уже настроено в графике бригады; дни услуги нужны для редкого случая
(«вывоз только по вторникам»).

**3. Онлайн-запись: согласен, что это страница КОМПАНИИ, а не галка у услуги?**
Сейчас нет ни ссылки, ни страницы, ни виджета, а `online_enabled = true` уже стоит у всех услуг —
в день запуска весь прайс опубликуется сам. *Рекомендация: сначала Кабинет → «Онлайн-запись»
(адрес, окна из графика команды), потом одна страница «Что можно записать онлайн» со всеми
услугами галками. Галка у услуги — последний шаг, а не первый.*
