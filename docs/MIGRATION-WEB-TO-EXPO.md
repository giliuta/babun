# Миграция: один код на iOS + Android + Web (удаление `apps/web`)

> ✅ **ВЫПОЛНЕНО 2026-08-25.** `apps/web` удалён, веб собирается из
> `apps/mobile` через `expo export --platform web`. Ниже — план, по которому это
> делалось, в редакции 2026-07-25; текущее состояние дерева — в
> `docs/architecture.md`.
>
> Статус на момент составления: **ПЛАН НА УТВЕРЖДЕНИЕ**, ничего не удалено и не
> изменено.

## 0. Короткий вывод

Цель («один код → iOS + Android + Web») достижима, и фундамент под неё уже заложен:
`react-native-web` уже в зависимостях, `app.json` уже содержит блок `web`, а в `packages/shared`
уже есть веб-реализации хранилищ (`storage/web.ts` на localStorage и IndexedDB-кеш `db/cache/index.ts`).

**Но одна посылка в постановке неверна и это главное, что нужно знать до решения:**

> «Удаляем только фронтенд, все данные в Supabase — ничего не теряем.»

Данные — да, в Supabase, и они не пострадают. Но `apps/web` — **не только фронтенд**.
Это ещё и работающий бэкенд: **14 серверных эндпоинтов**, из которых **четыре вызываются
извне** и сломаются молча, без ошибки в интерфейсе:

| Эндпоинт | Кто вызывает | Что сломается |
|---|---|---|
| `/api/stripe/webhook` | Stripe | Подписки/оплаты перестанут отражаться. Тихо. |
| `/api/twilio/status` | Twilio | Статусы доставки SMS (queued→sent→delivered) |
| `/api/calendar/[user_id]` | Apple/Google Calendar (подписки .ics) | У всех, кто подписался на календарь, лента умрёт |
| `/auth/callback` | Ссылки из писем Supabase | **Восстановление пароля и подтверждение регистрации** |

Expo Web — это **статический SPA** (`output: "single"`), сервера у него нет вообще.
Значит эти эндпоинты нужно не «перенести в веб-сборку», а **переселить в Supabase Edge Functions**
(там уже живут 4 функции: `account-delete`, `account-delete-cleanup`, `send_push`, `send_sms` —
инфраструктура знакомая).

Поэтому правильная формулировка задачи: **не «удалить веб», а «переселить бэкенд в Supabase,
интерфейс — в Expo, и только потом удалить веб»**. Удаление — последний шаг, а не первый.

## 1. Инвентаризация `apps/web`

72 страницы, 14 API-роутов, middleware, service worker.

### 1.1 Есть в мобильном — можно удалять смело

Календарь, клиенты (список, карточка, фильтры, теги, архив, CSV-импорт), чаты, финансы,
кабинет (услуги, команды, мастера, метки, города, категории, типы событий, типы объектов,
лояльность, SMS-шаблоны, счета, инвентарь, повторяющиеся, закрытие дня, незакрытые,
инсайты, аккаунт, доступ команды, синхронизация), инвойсы, авторизация, онбординг, инвайты.

**Финансы — проверил отдельно, раз они только что уехали на babun.app.**
Мобильные финансы **не отстают, а местами впереди**: есть переводы между счетами,
операции, счета, должники, разбивка прибыли, период-контрол, экспорт **и полноценные
инвойсы** (список/создание/редактирование/оплата/возврат/PDF), которых на вебе нет
в таком объёме. **Единственное, чего на мобильном нет — графики** (`FinancePieChart`,
`FinanceSparkline`). Это единственная потеря по финансам.

### 1.3 Серверная логика (14 эндпоинтов)

**Внешние вызыватели — критично (см. таблицу в §0):**
`stripe/webhook`, `twilio/status`, `calendar/[user_id]`, `auth/callback`.

**Держат секреты — нельзя унести в клиент:**
`invite`, `team/switch`, `account/delete`, `invoices/issue` (атомарная нумерация счетов через
уникальный индекс), `sms/test`, `feedback`, `feedback/submit`, `resolve-map-link`
(следует за редиректами коротких map-ссылок — из браузера невозможно из-за CORS),
`push/subscribe`, `push/unsubscribe`.

**Секреты, которым нужен новый дом:**
`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `TWILIO_ACCOUNT_SID/AUTH_TOKEN`,
`SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_SECRET_KEY`, `GITHUB_TOKEN`,
`SEND_SMS_FUNCTION_URL`, VAPID-ключи.

**Хорошая новость:** мобильное приложение **не вызывает ни один** из этих эндпоинтов —
оно работает напрямую с Supabase. То есть удаление веба **не сломает текущее мобильное
приложение**. Ломается веб-продукт и внешние интеграции, а не телефон.

`middleware.ts` — тривиален (проверка cookie перед `/dashboard`), замена не нужна.

## 2. Что мешает Expo Web (нативные зависимости)

| Зависимость | Web | Что делать |
|---|---|---|
| `react-native-mmkv` | ✗ нет web | Уже есть `packages/shared/storage/web.ts` (localStorage). Нужен `src/storage/mmkv.web.ts`, отдающий его |
| `expo-secure-store` | ✗ нет web | Используется только для ключа шифрования MMKV → на вебе ветка шифрования не нужна |
| `expo-sqlite` | ~ частично | Уже есть IndexedDB-кеш `db/cache/index.ts` + `MemorySqlAdapter`. Нужен `storage/sqlite.web.ts` |
| `@react-native-community/datetimepicker` | ✗ **нет web** | Нужна веб-замена (используется в экране записи) |
| `expo-contacts` | ✗ нет web | Скрыть «Из контактов» на вебе |
| `expo-haptics` | no-op | Безопасно |
| `expo-print` / `expo-sharing` / `expo-file-system` | ~ | PDF инвойсов на вебе — другой путь (Blob + download) |
| `expo-notifications` | ~ ограниченно | Web Push отдельно |
| `expo-image-picker`, `expo-document-picker`, `netinfo` | ✓ | ОК |
| `react-native-reanimated 4` + worklets | ~ | Требует настройки под web, версия свежая — риск |
| `nativewind 5.0.0-preview.4` | ~ | **Preview-версия.** Web-рендер на превью-релизе — главный технический риск |

**Архитектурно повезло:** MMKV используется ровно в двух файлах (`src/storage/mmkv.ts`,
`src/bootstrap.ts`), sqlite — тоже в двух. Всё уже спрятано за интерфейсы `KVStorage` и
`SqlAdapter` в shared. Платформенные шимы через `.web.ts` подхватит metro сам.

## 3. Порядок шагов (каждый шаг — проверяемый, ничего не ломается)

**Шаг 0. Решение по объёму** (см. §5 — вопросы). 0.5 дня.

**Шаг 1. Поднять Expo Web «как есть».** `bun run web`, шимы MMKV/sqlite/secure-store,
заглушки под datetimepicker и contacts. Цель — приложение открывается в браузере и логинится.
Веб-версия пока сырая, `apps/web` живёт. **Превью: dev-сборка на localhost.** ~3–5 дней.

**Шаг 2. Переселить бэкенд в Supabase Edge Functions.** 14 роутов → Deno-функции,
секреты в Supabase. **Стрелки Stripe/Twilio переключаются в их консолях, ICS-URL
проксируется со старого адреса.** `apps/web` ещё жив — работают оба, сравниваем.
Это самый ответственный шаг, деньги и SMS. ~5–8 дней.

**Шаг 3. Десктопный layout.** Мобильные экраны на мониторе 1440px выглядят полосой в 400px.
Нужны брейкпоинты, две колонки на широких экранах, hover/клавиатура.
**Это самая недооценённая статья затрат.** ~5–10 дней.

**Шаг 4. Портировать веб-онли функции** в Expo: админка, аналитика, аудит, доходы,
недостающие настройки, графики финансов. ~10–18 дней.

**Шаг 5. Публичные страницы.** Лендинг, `/book/[slug]`, `/feedback/[token]`, `/b/[token]`,
`/privacy`, `/terms`. SPA для них плох (SEO, скорость, ссылки из App Store).
*Рекомендация: НЕ тащить их в Expo, а оставить отдельной статикой* (см. §5, вопрос 2). ~3–5 дней.

**Шаг 6. Домен.** babun.app → Expo-сборка, старые пути 301-редиректами. Откат = вернуть DNS. ~2–3 дня.

**Шаг 7. Наблюдение 1–2 недели**, затем **удаление `apps/web`** отдельным коммитом.
Из `packages/shared` **ничего не выбрасывать** — `storage/web.ts` и IndexedDB-кеш становятся
реализациями для Expo Web.

## 4. Риски и честная оценка

| Риск | Тяжесть | Смягчение |
|---|---|---|
| Молчаливая поломка Stripe/Twilio/ICS | **высокая** | Шаг 2 до удаления, обе системы параллельно, проверка вебхуков в консолях |
| Ссылки `babun.app/terms` из приложения умрут → App Store | **высокая** | Юридические страницы держать живыми всегда (§5 в.2) |
| `nativewind@5.0.0-preview` на вебе | средняя | Проверить на шаге 1 до всех вложений |
| Десктопный UX | средняя | Шаг 3 отдельно и рано |
| Потеря Web Push | средняя | Мобильный push всё равно не собран — решить, нужен ли веб-push |
| Регресс отлаженного мобильного | средняя | Работать в ветке, шимы только через `.web.ts` |
| Админка без замены | средняя | Пока не портирована — держать веб или отдельный админ-деплой |

**Честная оценка: 6–10 недель** сфокусированной работы (~30–50 рабочих дней).
Это не «удалить папку». Дешёвая часть — поднять Expo Web (неделя).
Дорогие — бэкенд (2 недели), десктоп (2 недели), веб-онли функции (3 недели).

## 5. Вопросы, на которые нужен ответ до старта

1. **Кто реально пользуется babun.app сегодня?** Если только Артём — можно резать быстро
   и грубо. Если там живые клиенты/бригады — только поэтапно с параллельной работой.
2. **Публичные страницы (лендинг, запись, юридические) — тащим в Expo или оставляем
   отдельной статикой?** *Рекомендую отдельную статику:* SPA для SEO плох, а `/terms`
   и `/privacy` обязаны жить вечно ради App Store. Это ~5 файлов, отдельный крошечный
   деплой, и он не мешает принципу «одна правка → везде», потому что это не CRM.
3. **Админка** — нужна ли она на телефоне вообще, или это чисто десктопный пульт?
   Если десктопный — возможно, ей и место в отдельном маленьком приложении.
4. **Web Push** — нужен ли, или ждём нативный push на мобильном?

## 6. Куда встраивается единая карточка клиента

Работа по клиентам поставлена на паузу. Правильный порядок:

- Карточка живёт в `apps/mobile` — то есть делается **в той же кодовой базе**, которая
  после миграции станет и вебом. Ничего не пропадёт и не придётся переделывать.
- **Начинать её можно сразу, не дожидаясь миграции** — она не зависит ни от одного её шага.
- Единственное следствие миграции: когда включится десктопный layout (шаг 3), карточку
  нужно будет проверить на широком экране. Если делать её сразу «в одну колонку с
  max-width», этот пункт закроется сам.
