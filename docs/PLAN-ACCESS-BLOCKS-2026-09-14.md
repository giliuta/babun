## Контракт v1 — права по блокам (сервер 006 → экраны 008)

Окончательные решения владельца 14.09: у блока **три положения** — `off` (скрыт, данные на телефон не приходят) · `read` (данные приходят, запись отбивается) · `write`. Серых данных нет. Раздел, где у человека все блоки `off`, — на весь экран «Нет доступа». Новый сотрудник — всё `off`. Наборов нет. Календари — только явно выданные. Изменения — мгновенно.

Этот раздел — ЕДИНСТВЕННЫЙ источник формы данных для экранов. Меняется только новой версией (v2) с записью в журнале доски.

### Таблицы
- `public.access_blocks` — реестр, общий для всех компаний, пишут только миграции, читают все вошедшие.
  `key text primary key`, `area text` (`calendar | finance | clients | company | owner`), `scope text` (`calendar | company`), `levels text[]` (допустимые значения, первый — умолчание), `title_ru text`, `owner_only boolean`, `live boolean`, `enforced_by text[]`.
- `public.member_access` — уровни людей.
  `tenant_id uuid`, `user_id uuid`, `block text → access_blocks(key)`, `team_id text null`, `level text`, `set_by uuid`, `set_at timestamptz`.
  Уникально `(tenant_id, user_id, block, team_id) nulls not distinct`. `(tenant_id, user_id) → tenant_members on delete cascade` (увольнение стирает уровни). `(tenant_id, team_id) → teams(tenant_id, id) on delete cascade`.
  Триггер: у `scope = calendar` `team_id` обязателен; у `scope = company` — пустой; `level ∈ access_blocks.levels`; `owner_only` блоки не пишутся.
  **Нет строки = первое значение из `levels`** (для обычных блоков `off`).

### Значения уровней
- обычные блоки: `off | read | write`;
- `clients.scope`: `own | all` (умолчание `own` — «из его календарей»);
- `company.currency`: `read | write` (без валюты суммы не показать; скрыть нельзя);
- `owner.access`, `owner.billing`: `owner_only`, у сотрудника всегда недоступны.

### Ключи блоков v1
`calendar.records`, `calendar.create`, `record.status`, `record.amount`, `record.payment`, `calendar.day_labels` (все `scope = calendar`); `calendar.settings`; `finance.operations`, `finance.accounts`, `finance.debts`, `finance.documents`, `finance.close_day` (`calendar`); `finance.settings`; `clients`, `clients.scope`, `clients.contacts`; `services`; `masters`; `company.currency`; `company.profile`; `owner.access`; `owner.billing`. Экран берёт ключи и подписи ТОЛЬКО из `access_blocks`, строками в коде их не пишет.

### Функции (все `security definer`, ошибки — `42501` с `hint`)
- `my_access_map() → jsonb` — права вошедшего в АКТИВНОЙ компании:
  `{ "tenant_id", "is_owner": bool, "version": bigint, "company": { "<block>": "<level>" }, "calendars": { "<team_id>": { "<block>": "<level>" } } }`.
  Только `live` блоки. Владелец: `is_owner = true`, словари могут быть пустыми — экран считает всё `write`. Календарь, в котором у человека `calendar.records = off`, в `calendars` не попадает.
- `list_member_access(p_user_id uuid) → jsonb` — та же форма для сотрудника; только владелец.
- `set_member_access(p_user_id uuid, p_changes jsonb) → jsonb` — `p_changes = [{ "block", "team_id" | null, "level" }]`, одной транзакцией; возвращает новую карту этого человека.
  Только владелец активной компании; нельзя менять себя и другого владельца; блок должен быть `live`; уровень допустим; календарь из активной компании; `owner_only` отвергается.
  Отказы: `42501` `hint = 'access:not_owner' | 'access:target_owner' | 'access:not_live' | 'access:owner_only'`; `22023` `hint = 'access:bad_level' | 'access:bad_team' | 'access:bad_block'`.
- Отказ записи по правам в любом другом месте: `42501` с `hint = 'block:<key>'` — экран показывает причину из реестра и перечитывает карту.

### Мгновенное применение
- Приватный канал Realtime `access:<user_id>` (broadcast, авторизация по `realtime.messages`: слушать может только сам человек).
- Событие `access_changed`, полезная нагрузка `{ "tenant_id", "version" }` — без уровней. Получил → перечитать `my_access_map()`; если `version` не выросла — ничего.
- Шлёт триггер на `member_access` и на удаление из `tenant_members` (событие `membership_removed`, `{ "tenant_id" }` → стереть данные этой компании с устройства).

### Приглашения (этап Б, черновик — форма может уточниться)
- `create_invitation(p_email text, p_changes jsonb)` — та же форма изменений, что у `set_member_access`; письмо уходит всегда, ответа «есть ли аккаунт» нет.
- `my_invitations() → jsonb[]` — по подтверждённой почте вошедшего: `{ id, tenant_name, invited_by_name, calendars: [names], expires_at }`.
- `accept_invitation_by_id(p_id uuid) → { tenant_id, role, onboarded, access }` — `access` в форме `my_access_map()`; экран кладёт роль и карту в память ДО перехода.
- Канал `invitations:<user_id>`, событие `invitation_received`.

### Телефон до этапа SMS
`auth.users.user_metadata.phone` (E.164, пишет экран регистрации) + `phone_verified: false`. Сервер нормализует сам и не считает его подтверждённым. Переезд в `auth.users.phone` — только через SMS-подтверждение.

### Что `live` и когда
- Этап 1: реестр заведён, все блоки `live = false`, `set_member_access` отвечает `access:not_live` — экран можно строить на тестовых данных.
- Этап 2: `calendar.*`, `record.*`, `finance.*` → `live`. Этап 5: `clients*`. Этап 7: `masters`, `services`. Этап 8: `company.*`.

# Доступ сотрудников по блокам: итоговый план (14.09, после проверки)

## 0. Коротко

- **Суть рекомендации прежняя.** Это смесь четырёх моделей:
  - список блоков хранится как данные (из D);
  - у каждого человека свой уровень по каждому блоку, при приглашении уровни заполняет пресет (из A, без живого шаблона);
  - права стираются вместе с членством в компании (из C);
  - валюту и реквизиты меняют отдельные узкие функции, сервер проверяет теми же приёмами, что уже работают (из B).
- **Положений у блока на экране четыре:**
  - Выключен — блока нет.
  - Нет доступа — блок серый и пустой, данные на телефон не приходят.
  - Смотрит — данные приходят, форму можно править, «Сохранить» серая и называет причину.
  - Меняет — всё доступно.

  Сервер различает три: нет, чтение, запись.
- **Что изменила проверка, главное:**
  1. (после проверки) **Суммы и телефоны прячет сервер, а не экран.** Сотрудник со своим входом может спросить сервер напрямую, мимо приложения. Такая дыра есть уже сейчас: мастер с правом на календарь может прочитать суммы записей этого календаря.
  2. (после проверки) **Пресеты не открывают больше, чем открыто сейчас.** «Мастер» получает только выбранные календари. «Диспетчер» в выбранных календарях видит клиентов только этих календарей.
  3. (после проверки) **Пока старые и новые права живут вместе, пишет их одна функция.** Экран «Доступ» выходит после Клиентов, а не до них.
  4. (после проверки) **Сторож проверяет поведение, а не текст.** Тестовый человек без права обязан получить отказ.
  5. (после проверки) **Первый кадр у сотрудника без серого мигания.** Уровень понизили — данные блока стираются с телефона, а не просто сереют.
- **Сроки (после проверки).**
  - Календарь, Финансы, Клиенты и экран «Доступ» — ≈25–33 рабочих дня.
  - Всё, включая Услуги, Мастеров, реквизиты и снос старого, — ≈30–38 дней, это 6–8 недель одной сессии.
  - Это на 6–9 дней дороже прежней оценки.
  - Первое, что можно потрогать руками, будет через ≈9–11 дней (§6, этап 2).
- **Переход сейчас дешёвый.** Проверено запросом к боевой базе 14.09, только чтение:
  - 19 компаний, в каждой только владелец;
  - сотрудник один — мастер с правом `view` на один календарь;
  - диспетчеров нет;

Реестр блоков как данные** (`blocks` + `block_permissions` на человека × блок × календарь или компанию) | Ближе всех к решению 14.09; реестр сам знает, где сервер защищает блок | ≈15–18 дней, дальше +2–3 дня на экран | **Три дефекта.** Умолчания по роли живые — новый блок молча открывается всем. Увольнение права не стирает. Новые календари пропадают | Да |
| **Смесь (рекомендую).** Реестр из D + уровни, которые пресет записывает (из A) + стирание вместе с членством (из C) + узкие функции и проверенные приёмы сервера (из B) | Всё из решения 14.09; одна правда о правах; переключатель появляется на экране, только когда сервер его уже проверяет; новые календари не пропадают | (после проверки) До экрана «Доступ» ≈25–33 дня, всё ≈30–38 | (после проверки) До этапа 9 права лежат в двух таблицах: пишет одна функция, сторож сверяет. Суммы и телефоны прячет сервер, иначе «Нет доступа» у них — пустое обещание | Да |

**«Мгновенно» от модели не зависит.** Сейчас приём приглашения переключает компанию без роли (`invitations.ts`: `switchTenant(tenantId, { onboarded: true })`), и экран сначала идёт за ролью в сеть. Лечится одинаково в любой модели.

## 3. Рекомендация: как устроено

### 3.1 Почему смесь

1. Решение 14.09 — права на человека по блокам, с уровнями. A и C не умеют «в одном календаре можно, в другом нельзя». B не умеет валюту и мастеров без костыля. D умеет обе вещи, но с тремя дефектами, и смесь их убирает.
2. Пресет не хранится отдельной правдой, он записывает строки. Изменили пресет — у существующих сотрудников ничего молча не меняется.
3. Требование «каждая функция в обход зовёт то же правило, что и таблица, и это охраняет сторож» ложится на список мест проверки в реестре (`access_blocks.enforced_by`).
4. **Изоляция компаний не ослабляется.**
   - Первым условием каждого правила таблицы остаётся `tenant_id = (select current_tenant_id())`.
   - `current_tenant_id()` подтверждает членством и заголовок компании, и токен (`20260913010000`).
   - Уровни ссылаются на `tenant_members` и `teams(tenant_id, id)`, поэтому не могут указать на чужую компанию.
   - (после проверки) Функции прав берут уровни только из активной компании, а «владелец ли» — из членства в этой же компании. Иначе строка «во всех календарях» из компании A сработала бы в компании B.

- Область: К — уровень может отличаться по календарям; Ко — один уровень на всю компанию.
- Пресеты: М — «Мастер», Д — «Диспетчер», Я — «Как у меня».

(после проверки) Пресеты не открывают больше, чем открыто сейчас. Это доказывается сверкой на боевой («до» равно «после» для каждого живого человека), а не просто утверждается.

**Правила блока «Календарь и записи»** (после проверки):
- **Своя работа.** Запись, где человек назначен мастером, видна ему в любом календаре. Так мастер работает сейчас: `list_master_appointments_safe` показывает записи с `master_id = мой`.
- **Проверяется новый календарь.** Перенести запись можно только туда, где у человека «Меняет». Сейчас `appointments_update` это уже проверяет — при переписывании правил это нельзя потерять.
- **Чужого клиента не привязать.** В записи может стоять только клиент, которого человек уже видит. Иначе запись с известным номером любого клиента открывает этого клиента вместе с телефонами. Номера клиентов диспетчер видит, например, в долгах.
- **Кто меняет только статус и заметку**, не трогает календарь, мастера, клиента, дату и время: эти колонки относятся к «Календарь и записи».
- **«Сумма» отделена от «Оплаты».** Раньше «Итого» стояло в блоке услуг, а сумма числилась за оплатой, и мастер увидел бы цены строк с пустым итогом. Если позже понадобится «менять услуги, не видя сумм», это отдельный заход: сумму считает сервер, +2–3 дня.
- **«Оплата: Смотрит» у Диспетчера** следует починке 14.09: принять оплату приглашённому диспетчеру уже нельзя без права `finance`. Предоплату он пока ставить может, а в новой схеме она тоже относится к «Оплате». Диспетчеров в базе нет, сужать некого.

### 3.3 Где хранится

1. **`public.access_blocks`** — реестр блоков, общий для всех компаний (без `tenant_id`). Назван не `blocks`, чтобы не путать с «блоками записи» в настройках.
   - Колонки: `key`, `area`, `scope` (`calendar` | `company`), `levels` (из `off, none, read, write`), `title_ru`, `preset_master`, `preset_dispatcher`.
   - `enforced_by text[]` — где проверяется блок: правила таблиц, функции, триггеры, серверные функции.
   - `live` — сервер уже проверяет этот блок; только такие видны на экране владельца.
   - Читают все вошедшие, пишут только миграции.
2. **`public.member_access(tenant_id, user_id, block, team_id null, level, set_by, set_at)`** — уровни сотрудников.
   - `team_id null` значит «во всех календарях, включая будущие». Строка с календарём — исключение для этого календаря.
   - (после проверки) Исключение **заменяет** общий уровень в обе стороны: может и поднять, и опустить. Тест: общий «Смотрит» плюс календарь Y «Нет доступа» — Y закрыт.
   - (после проверки) Уникальность — `unique nulls not distinct (tenant_id, user_id, block, team_id)`, а не через `coalesce(team_id,'*')`. `teams.id` — текст, и календарь с номером `*` возможен. База на Postgres 17, так писать можно.
   - Связи: `(tenant_id, user_id) → tenant_members on delete cascade` (увольнение стирает уровни); `(tenant_id, team_id) → teams(tenant_id, id) on delete cascade`.
   - Триггер пропускает только допустимый уровень; у блока компании `team_id` должен быть пустым.
   - Свои строки видит сам человек, все строки — владелец. Объём ничтожный: 10 сотрудников × ~25 блоков.
3. **Пишет одна функция — `set_member_access`** (после проверки).
   - Вызывает только владелец; менять себя и другого владельца нельзя.
   - Сервер проверяет: ключ есть в реестре и помечен `live`; уровень допустим; календарь из активной компании; блоки «только владелец» не выдаются. Отказ — `42501`. Так же проверяет `create_invitation(…, p_access)`. Тест: чужой календарь и выдуманный ключ отвергаются.
   - До этапа 9 она в той же транзакции пишет и `calendar_members`: эту таблицу читают старые правила.
   - Через неё идут приглашение (`grant_invitation_calendar`), смена роли и экран «Доступ». Сейчас смена роли (`useUpdateTenantMember`) пишет в `tenant_members.role` напрямую.
   - Сторож следит, чтобы две таблицы говорили одно и то же. Иначе приглашённый после переноса получил бы пустую компанию, а смена роли молча ничего бы не меняла.
4. **`public.invitations`** получает колонку `access jsonb`: пресет, календари, исключения. `team_id` остаётся на время перехода.
5. **Перенос сегодняшних прав.**

   | Сейчас | Станет |
   |---|---|
   | `view` | «Календарь и записи: Смотрит» в этом календаре |
   | `edit_all` | «Календарь и записи: Меняет» + (после проверки) «Сумма записи: Меняет» |
   | `book` | «Новые записи: Меняет» |
   | `clients` | «Клиенты: Меняет» + «из его календарей» |
   | `finance` | «Доходы и расходы: Меняет» + «Счета: Смотрит» + (после проверки) «Оплата в записи: Меняет» |
   | `phones`, `settings`, `close_day` | не переносятся: их не читает ни одно правило и ни одна функция |
   | Строки владельцев (перенос 12.09) | не переносятся: владелец не ограничивается |
   | Диспетчер без строк прав | пресет «Диспетчер» во всех календарях — так он работает сейчас (таких нет) |
   | (после проверки) Мастер без строк прав | строки **только** по календарям, куда он назначен (`masters.team_id`, `teams.lead_ids`, `helper_ids`, `members`); «во всех календарях» — никогда (таких нет) |
   | (после проверки) Мастер со строками | его календари + календари по назначению + своя работа: сейчас `list_master_appointments_safe` показывает ему всё это сразу (такой мастер один) |

   (после проверки) Правильность переноса доказывается прогоном на боевой с откатом (`begin/rollback`). У каждого живого человека видимые записи, клиенты и календари до и после должны совпасть.

   После этапа 9 таблица `calendar_members` и функции `current_user_calendar_ids`, `current_user_has_calendar_grants` сносятся.
6. **`tenant_members.role`.** `owner` остаётся владельцем. `dispatcher` и `master` становятся просто подписью пресета. `master_id` связывает человека с карточкой мастера.

### 3.4 Как проверяет сервер

**На каждый блок одно правило.** Две функции, обе `stable security definer`:
- `access_calendars(p_block, p_min) returns text[]` — календари, где уровень не ниже `p_min`;
- `access_company(p_block, p_min) returns boolean` — то же для блоков компании.

Как они решают:
- владелец — всё;
- нет членства — ничего;
- нет строки — «нет»;
- неизвестный ключ — «нет»;
- (после проверки) уровни берутся только из активной компании, исключение календаря заменяет общую строку, своя работа — отдельное условие блока записей.

В правиле таблицы вызов пишется только подзапросом. Голый вызов считается на каждую строку — так уже было, 4778 мс против 87.

```sql
create policy finance_transactions_select_calendar on public.finance_transactions for select to authenticated
using (
  tenant_id = (select public.current_tenant_id())
  and team_id in (select unnest(public.access_calendars('finance.operations','read')))
);
```

**Четыре вида проверки.** Какой вид у блока, записано в `enforced_by`.
1. **Строки — правило таблицы.**
   - (после проверки) При сохранении правило (`with check`) смотрит на новые значения.
   - Календарь должен быть тем, где у человека «Меняет».
   - Клиент — тем, кого человек видит.
   - Счёт операции — тем, что виден в его календаре.
2. **Колонки внутри строки — триггер `before insert or update`.**
   - (после проверки) Триггер срабатывает первым по имени и сравнивает только то, что поменял человек.
   - Колонки, которые сервер выводит сам (`payment_status` в `protect_paid_appointment_finance`), не считаются.
   - Отказ — `42501` с `hint = 'block:<ключ>'`, по образцу `enforce_plan_limits`.
   - Тест: человек с «Сумма: Меняет» и «Оплата: Нет» может поменять услуги; человек с «Сумма: Нет» получает отказ и заранее видит на экране серую причину.
3. **Скрытые колонки: суммы и оплаты в записи, телефоны клиента** (после проверки). Правило таблицы отдаёт строку целиком и колонки не прячет. Поэтому так:
   - Строку `appointments` целиком читают только владелец и тот, у кого «Сумма» и «Оплата» не ниже «Смотрит».
   - Остальные получают записи **только через окно**. Окно — функция в обход с тем же правилом календаря, которая отдаёт суммы пустыми. Пишут такие люди через функцию с белым списком колонок.
   - Это уже работающий путь мастера (`list_master_appointments_safe`, `update_master_appointment_safe`). Разница в том, что выбирает его уровень, а не роль.
   - Живые обновления таким людям приходят сигналом без строки (`realtime.broadcast` из триггера): `postgres_changes` требует права читать таблицу.
   - Клиенты — тем же способом, через обобщённый `list_master_clients_safe`.
   - Сторож: прямой запрос `GET /rest/v1/appointments?select=total_amount,payments` под сотрудником без права должен вернуть пусто, иначе миграция не накатывается.
   - Почему не «представление плюс запрет чтения таблицы». Представлению `security_invoker` самому нужно право читать таблицу. А отнять права на колонки у всех — значит переписать и все чтения владельца.
4. **Колонки компании** — узкая функция на одно действие (`set_tenant_currency`, `update_company_profile`). Строка `tenants` сотруднику не открывается никогда.

**Функции в обход.** Пять уже слушают права по календарям (сделано 14.09). На этапе 2 они переходят на `access_*` вместе с теми, что пока решают только по роли:
- клиенты: `create_client_with_tags`, `list_master_clients_safe`, `current_user_can_access_client`;
- деньги: `replace_day_extras`, `record_account_transfer`, `delete_account_transfer`, `account_balances`, `account_period_totals`, `list_payment_accounts_safe`, `cancel_invoice`;
- справочники и компания: `list_dispatcher_services_safe`, `list_operational_masters_safe`, `patch_master_profile`, `current_tenant_profile_safe`;
- записи: `update_master_appointment_safe`, `list_master_appointments_safe`.

Функции, которые законно доступны только владельцу (`tenant_data_export`, `create_invitation`), идут в явный список исключений.

**Сторож** (после проверки: главный слой — поведение).
- **Поведение.** Для каждого живого блока — прогон на боевой с откатом.
  - Три тестовых человека («Нет», «Смотрит», «Меняет») против правила таблицы и каждой функции из `enforced_by`.
  - «Нет» — ноль строк или `42501`. «Смотрит» — чтение есть, запись `42501`. «Меняет» — всё проходит.
  - Мутант: нарочно убрали проверку из одной функции — прогон обязан упасть.
- **Текст — только в помощь.**
  - Тело функции берётся из `pg_get_functiondef` без комментариев.
  - Сторож ловит `execute`, чтение через представления и вызовы других функций в обход.
  - Форма `(select access_*)` проверяется в `pg_policies.qual/with_check`, а не в телах функций.
  - Нынешний сторож `20260912330000` ищет вызовы с пустыми скобками и не видит вызовов с аргументами.
- **Серверные функции** (`supabase/functions/*`).
  - Любая функция, которая читает таблицы компании ключом `service_role`, либо зовёт функцию с правилом блока, либо стоит в списке исключений.
  - Лента для внешних календарей `calendar-ics` в коде есть, а на боевой не выложена: выложены только `send_push` и `send_sms`.
  - Ключ ленты — номер человека, а приложение само раздаёт этот номер в поле `created_by` каждой записи. По номеру владельца лента отдала бы расписание всей компании с адресами.
  - Выкладывать её можно только с отзываемым ключом на пару «человек × компания» и с чтением через `access_calendars`.
- **Экран.** Список ключей блоков генерируется из `access_blocks`, тест проверяет, что каждый ключ в `useAccess` есть в реестре. Иначе опечатка покрасит блок серым у сотрудников, а владелец этого не заметит: у него всё открыто.

### 3.5 Как экран красит серым и называет причину до нажатия

- **Карта уровней.**
  - RPC `my_access_map()` отдаёт уровни; хук `useAccess(block, teamId?)` возвращает положение блока и фразу причины.
  - Ключ кэша лежит в `lib/company-query-keys.ts`, копия карты — в MMKV, её читает первый кадр.
  - Карта опрашивается раз в 60 с (у `["my-calendars"]` сейчас опроса нет) и сбрасывается при любом отказе с `hint block:*`.
- **Первый кадр без мигания** (после проверки).
  - Приём приглашения, регистрация по ссылке и находка приглашения по почте отвечают `{tenant_id, role, onboarded, access}`.
  - Роль ложится в память приложения, карта — в MMKV, и всё это **до** перехода на экран.
  - Сейчас приём зовёт `switchTenant` без роли, а регистрация по ссылке уходит на `/onboarding` вообще без ответа (`register.tsx`).
  - Условие приёмки: в первом кадре нет серого.
- **Пока карты нет**, блок в положении «Нет доступа», никогда не «Смотрит». (после проверки) Исключение — владелец: его роль берётся из сохранённой, и его собственный экран серым не мигает.
- **Данные привязаны к уровням** (после проверки).
  - Сейчас ключ данных — «компания + роль» (`company-query-keys.ts`), у денег — только компания.
  - В ключи данных блока добавляется версия уровней этого блока.
  - Уровень понизили — данные блока явно стираются из памяти приложения, из копии на диске и из прогрева.
- **Один проп на канонических блоках** (`SectionCard`, `PaymentBlock`, `ReferenceBlock`, `DayFinanceFooter`, `DayFinanceSheet`, плитки финансов):
  - `off` — блок не рисуется;
  - `none` — шапка и серая строка «Нет доступа · открывает владелец», запросы данных выключены;
  - `read` и `write` — как сейчас.

  Точный вид серого выбираем вариантами рядом в симуляторе (правило 5.1).
- **Страница записи `/book`.**
  - Изменения считаются по блокам.
  - «Сохранить» нажимается, когда форма заполнена и все изменённые блоки в положении «Меняет».
  - Причина видна до нажатия: «Время меняет владелец» и кнопка «Вернуть».
  - На сервер уходит только изменённое. Сейчас `buildPatch` шлёт всю форму, и сторож колонок отбил бы даже правку заметки.
  - (после проверки) Офлайн-очередь уже везёт правку, а не всю строку (`appointmentsCached.ts`: `payload: patchToRow(patch)`). Значит, чинить надо того, кто собирает правку. Тест на повтор из очереди всё равно нужен.
- **Календарь.** Шестерёнка, тап по слоту (лист с серой «Записать» и причиной), меню долгого нажатия (пункты серые с причиной), метка дня и полоса денег — всё решает `useAccess`, а не роль.
  - (после проверки) Жест, который сохраняет сразу (перетащить запись), при «Смотрит» не срабатывает и сразу показывает причину.
  - Форму править можно, потому что у неё есть отдельная «Сохранить». У жеста такой кнопки нет. Это исключение записано в правиле 10.
- **Лента календарей** (после проверки).
  - Календарь с «Нет доступа» — серый чип с именем и замком; выключенный календарь — без чипа.
  - Сейчас `list_my_calendars` вообще не отдаёт календари без прав. Теперь она будет отдавать их имя и цвет.
  - Это новое узкое чтение, оно отмечено в этапе 4.
- **Роль перестаёт выбирать путь данных.** Сейчас экраны решают по роли в 111 местах в 32 файлах (`role ===`, `isCrew`, `can(role…)`), плюс `RoleCapabilityBoundary` и `canAccessCabinetPath`.
- **Синхронизация** (после проверки).
  - Живые обновления (`SyncBridgeMount`) получает каждый член компании. Кому строку читать нельзя — получает сигнал без строки.
  - Очередь и копия на диске (`SyncRuntimeMount`, `babun-cache.db`) — только при «Меняет» у записей или у клиентов.
  - Остальные сохраняют статус и заметку только при сети, как мастер сейчас.
  - Иначе «Статус: Меняет» у пресета «Мастер» положило бы мастерам на диск клиентов и записи. Сейчас этого нет (`AppProviders.tsx`: только owner и dispatcher).
- **Отказ сервера — последняя линия.** Тост называет блок из реестра. Правка из очереди не пропадает молча: в панели очереди строка «не сохранено: нет права».
- **Что после этапа 4 ещё закрыто целиком** (после проверки, временно):
  - вкладка «Клиенты» у мастера (сейчас `operate-clients` на весь экран) — до этапа 5;
  - экраны кабинета вне шести областей (лояльность, блоки записи, способы связи, метки и другие) — пока до них не дойдёт очередь, ~½–1 день на экран.

### 3.8 Правило 10 канона, новая редакция

Заменяет «права выдаются на календарь» и пункты 1–2 (`AGENTS.md`, строки 346–374).

(после проверки) По сравнению с прошлой редакцией добавлено:
- исключение по календарю заменяет общий уровень;
- владельческие блоки у сотрудника серые;
- ключи блоков на экране — только из реестра;
- колонки прячет сервер;
- сторож проверяет поведение;
- жесты при «Смотрит» не срабатывают и называют причину;
- при понижении данные блока стираются с телефона.

> Права выдаются ЧЕЛОВЕКУ ПО БЛОКАМ (`public.member_access`). Блок — строка реестра `public.access_blocks`. У календарного блока уровень может отличаться по календарям; исключение по календарю заменяет общий уровень.
>
> Положения: Выключен (блока нет) · Нет доступа (серый и пустой, данные на телефон не приходят) · Смотрит (данные приходят, форма правится, «Сохранить» серая и называет причину) · Меняет. **По умолчанию — серый, не скрытый.** Скрыт только блок, который владелец выключил этому человеку. Блоки «только владелец» у сотрудника серые с причиной.
>
> Новый блок заводится с тремя ответами в том же коммите:
> 1. Ключ в реестре и допустимые положения. Ключ на экране берётся только из реестра.
> 2. Что приходит при «Смотрит» и что НЕ приходит при «Нет доступа». Если блок — колонки внутри строки, их прячет сервер: без права строку не читают напрямую, а получают через окно без этих колонок. Спрятать на экране — не считается.
> 3. Где сервер проверяет чтение и запись. Правило таблицы и КАЖДАЯ функция в обход зовут одно правило блока; их имена перечислены в `enforced_by`. Сторож проверяет поведением: человек с «Нет» и «Смотрит» получает отказ и от таблицы, и от каждой функции из списка.
>
> «Видно, но при нажатии ошибка» не бывает. Жест, который сохраняет сразу, при «Смотрит» не срабатывает и сразу называет причину. Прогрев и кэш берут только блоки с «Смотрит» и выше; при понижении данные блока стираются с телефона.

## 4. День сотрудника

Пример: приглашён в «Команду 1» с пресетом «Мастер». Владелец поднял ему «Сумму записи» до «Смотрит».

1. **Приглашение.** Сейчас это ссылка `babun://invite/<токен>` через «Поделиться»; писем сервер не шлёт (вопрос 3). На экране приглашения видны только первая буква email и домен.
2. **Регистрация.** Своим email и паролем. Это его собственный аккаунт, а не суб-аккаунт владельца.
   - Членство и уровни записывает одна функция.
   - Право на календарь при регистрации по ссылке уже выдаётся (14.09).
   - (после проверки) Если в вопросе 3 выберете подтверждение почты, между регистрацией и компанией будет письмо.
3. **Первое открытие.** Та же компания и те же четыре вкладки, что у владельца.
   - (после проверки) Роль и карта уровней уже на телефоне к первому кадру: ни серого мигания, ни крутилки.
   - Записи недели приходят одной волной, примерно за полсекунды.
   - В ленте «Команда 1» живая, второй календарь компании серый с замком — видно только имя.
4. **Нет доступа — серое.**
   - Вкладка «Финансы»: плитки серые и пустые.
   - Полоса «Доход / Расход» без цифр, шестерёнка серая.
   - Тап по свободному слоту открывает лист с серой «Записать» и подписью «Новые записи создаёт владелец».
   - В записи блок «Оплата» серый: «Оплату принимает владелец».
5. **Не видит вовсе.** Блоки, которые владелец выключил (например, «Долги»), и выключенные календари.
6. **Смотрит.** В записи все блоки на месте, суммы видны.
   - Время можно поменять в форме, но «Сохранить» серая: «Время меняет владелец · Вернуть».
   - (после проверки) «Выбрать услугу» серая: «Услуги меняют сумму — меняет владелец».
   - (после проверки) Перетащить запись в сетке нельзя: карточка не поднимается, сразу появляется подпись «Переносит владелец».
7. **Меняет.** Статус и заметку — сохраняется сразу. (после проверки) Только при сети: офлайн-очереди у него нет, как у мастера сейчас.
8. **Сохранение без права.** Кнопка не нажимается.
   - Если старая сборка всё же отправила правку, сервер отвечает `42501 block:calendar.records`.
   - Экран показывает ту же фразу и перечитывает карту уровней.
   - (после проверки) Данные блока, у которого понизили уровень, стираются с телефона.
9. **Что лежит на его телефоне.**
   - (после проверки) Всё в памяти, на диске ничего.
   - Записи «Команды 1» и его собственные записи в других календарях, клиенты этих записей с телефонами, услуги, мастера.
   - Денег компании, чужих клиентов и записей второго календаря там нет.
   - (после проверки) Прямым запросом к серверу мимо приложения он их тоже не получит.

## 5. День владельца

   - Совсем мгновенно — через подписку на `member_access`, это ещё полдня работы.
   - (после проверки) Понизили до «Нет доступа» — данные блока стираются с телефона, а не просто сереют.

   - Строка `tenant_members` удаляется, уровни уходят вместе с ней.

4. **Позвал того же человека снова.** Он получает то, что выбрано в новом приглашении. Сейчас наоборот:
   - `useRemoveTenantMember` удаляет только членство;
   - `calendar_members` переживает увольнение;
   - выдача прав пишет `on conflict do nothing`;
   - в итоге оживают старые права.
5. **Сменил сотруднику роль** (после проверки). Это смена пресета через ту же функцию-писателя. Сейчас `useUpdateTenantMember` меняет только подпись роли в `tenant_members`, а права остаются прежними. Разжалованный владелец остался бы вообще без строк прав, то есть с пустой компанией.

## 7. Что решает владелец: три вопроса

**1. Какой пресет стоит первым при приглашении?** Рекомендую «Мастер».
- **«Как у меня».**
  - В первую же минуту на личный телефон нового человека уходят вся клиентская база с телефонами и деньги компании.
  - (после проверки) Не только в память: у такого человека «Меняет» у записей и клиентов, значит, копия ложится и на диск (`babun-cache.db`).
  - Ошиблись с человеком — скачанное уже не вернуть.
- **«Диспетчер»** (после проверки).
  - На телефоне записи выбранных календарей с суммами и клиенты этих календарей с телефонами, есть копия на диске.
  - Денег компании, приёма оплаты, реквизитов и настроек календаря нет.
- **«Мастер»** (после проверки).
  - Календари выбираются обязательно.
  - На телефоне записи этих календарей и его собственные записи, их клиенты с телефонами, услуги. Сумм нет, на диске ничего.
  - Цена: диспетчеру вы один раз переключаете пресет — около минуты на человека.

**2. Новый календарь, заведённый после приглашения, сам открывается сотрудникам с доступом «во всех календарях»?** Рекомендую «да». (после проверки) Вопрос касается только тех, кому вы сами выбрали «во всех календарях»: у «Мастера» так по умолчанию не бывает.
- **Цена «да»** (после проверки, целиком). Записи нового календаря и история клиентов, у которых там есть записи, сразу уходят на телефоны всех, у кого «во всех календарях». Так будет, пока вы не поставите исключение.
- **Цена «нет».** У каждого сотрудника новый календарь серый (видно только имя), пока вы не откроете его в карточке каждого.

**3. Как убедиться, что зарегистрировался именно ваш сотрудник?** Сейчас регистрация сразу считает почту подтверждённой: так у 17 из 19 аккаунтов боевой базы. Рекомендую подтверждение почты.
- **Цена «подтверждение почты».**
  - (после проверки) Между «зарегистрировался» и «открыл компанию» появляется письмо и возврат из письма в приложение. Такого возврата сейчас нет: `emailRedirectTo` не задан.
  - Подтверждение включается для всех регистраций, новые владельцы тоже подтверждают почту.
  - Членство и уровни записываются только после подтверждения, при регистрации по ссылке тоже. Разбираться с уже вошедшими без подтверждения почти не с кем: сотрудник в базе один.
  - Зато «добавил по email → он зарегистрировался → готово» работает буквально: сервер сам находит приглашение по подтверждённой почте (`claim_my_invitations`), ссылка остаётся запасной.
  - Это ≈1,5–2 дня.
- **Цена «как сейчас, по ссылке».**
  - Мгновенно, без письма.
  - (после проверки) Но ссылка работает как ключ. Кто её получил и знает email сотрудника, может зарегистрироваться под этим email раньше него и получить всё, что выбрано в пресете.
  - Ссылку вы пересылаете сами, и без установленного приложения она не откроется.

**Уже решено, не спрашивать:**
- права на человека по блокам с уровнями, «Клиенты» — уровень у каждого сотрудника (14.09);
- по умолчанию блок серый, скрыт только выключенный (13.09);
- вкладок всегда четыре, внутри «нет доступа» (13.09, `app/(dashboard)/_layout.tsx`);
- другие компании греются заранее (13.09, `9d1549e2`).
