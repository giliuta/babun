## Решения владельца (три раунда)

### Раунд 1 — что строим

> В записи над «Оплатой» — блок со счетами из финансов. Счетов нет — кнопка
> «Создать счёт». Бригадир тапает счёт, на который оплатили, и деньги заходят
> в финансы на этот счёт. В настройках счёта — показывать его в оплате или
> нет. Продумать наперёд сплит, предоплату и всё, что понадобится. Это блок
> завершения: тапнул — запись закрыта; не тапнул — запись автоматически
> становится долгом. Следующий шаг — чек или инвойс. Сначала доход.

### Раунд 2 — ответы на первый план

- **Р1.** Тап по счёту = оплачено полностью, сейчас. Предоплата — явный
  режим сверху. Инвойс: счёт компании выставлен, деньги через две недели —
  запись фиксируется как «инвойс, не оплачен».
- **Р2.** Без счетов — только «Создать счёт». Блок можно выключить в
  Кабинет → «Запись»; тогда доход фиксируется на единый счёт команды.
- **Р3.** Счёт принадлежит одной команде; единого счёта на все команды пока
  нет; в команде нет двух счетов с одним именем (уже так в базе и в листе).

### Раунд 3 — ответы на уточнения (2026-09-06)

- **Р4. Любые деньги до визита — предоплата.** Только режимом «Предоплата».
- **Р5. Часть на месте бывает:** «200 € наличкой и 100 € на карту».
- **Р6. Без черновика.** «Не нравится выполнять несколько действий» — тап
  пишет сразу. Рекомендация «черновик + кнопка» отклонена, принимается
  решение владельца.
- **Р7. Долг — по времени окончания.** Запись на 11:00, выполнена до 15:00,
  расчёта нет → долг, «пока кто-либо не зайдёт в запись и не выберет оплату».
- **Р8. Снять оплату.** Бригадир нажал «на карту», деньги не поступили —
  владелец и сам бригадир могут в любой момент снять эту сумму, запись
  возвращается в долг: «якобы не оплачено, деньги не зашли по факту».
- **Р9. Возвраты — не сюда.** Почти не используются; в блоке их нет. Долг не
  списывается — «просто переводится до момента оплаты»; если денег не будет,
  запись отменяют или скрывают.

## Пределы движка (по телам функций в базе)

1. Проводки строятся из скалярных колонок записи; каждое изменение — дельта
   одной строкой на счёт из `payment_account_id`. Несколько платежей на разные
   счета = несколько последовательных записей. При «пишем сразу по тапу» это
   получается само: один тап — одна дельта.
2. После первой доплаты сторож пропускает только оплату и завершение.
3. Роль `master` пишет только `status`/`comment` → без RPC бригадир оплату не
   запишет и не снимет (Р8).
4. Снятие денег сегодня = уменьшение целей → `reconcile` пишет «Возврат» с
   новейших строк (LIFO), а не с конкретного платежа: сняв «карту 100» после
   «наличных 200», сторнируем не тот счёт. По платежу снимать умеет только
   RPC, которая пишет сторно сама против нужной строки дохода — образец
   `settle_appointment_from_invoice_payment` (контекст, который `reconcile` и
   сторож пропускают).
5. Дата проводки = рабочий день тенанта в момент записи на сервере; RPC с
   `p_paid_at` это закрывает.
6. Долг считается только у `status = completed`; статус сам не меняется.

## Модель оплаты

### Словарь

- **Счёт** — куда лежат деньги команды; в блоке — активные с «показывать в оплате».
- **Платёж** — событие «столько-то легло на такой-то счёт тогда-то».
- **Предоплата** — деньги до начала визита; **остаток** — итог минус получено;
  **долг** — остаток по визиту, время окончания которого прошло.
- **Инвойс** — счёт компании клиенту; запись «ждёт оплаты» до `due_on`,
  после — «просрочен».
- **Сплит** — несколько платежей на разные счета по одной записи.
- **Снять оплату** — платёж отменён, потому что деньги не поступили; не
  возврат клиенту.
- **Закрыть визит** — статус «Выполнена».

### Инварианты

- Сумма платежей ≤ итог; деньги — центы, два знака.
- Способ выводится из вида счёта, человек его не выбирает.
- «Куда легло» — у платежа, не у записи.
- Зеркала записи пишет только сервер (RPC 066); клиент шлёт событие.
- Один счёт = одна команда; имя уникально в команде.

### Правила блока

- **П1. До начала визита** (по времени начала записи в рабочем поясе
  тенанта) деньги принимаются только режимами: «Предоплата» — поле суммы
  (подставлен весь остаток, правится) → тап по счёту → записано; «Инвойс» —
  редактор инвойса из записи. Плитки без режима неактивны, подпись «Визит ещё
  не начался — предоплата или инвойс» (Р4).
- **П2. С начала визита** тап по счёту = получено полностью, **записано
  сразу**, статус «Выполнена» (Р1, Р6). Часть: сначала тап по сумме остатка
  (число редактируется) → тап по счёту → записана часть; остаток остаётся,
  плитки активны для следующего счёта. «200 наличкой + 100 на карту» = правка
  суммы и два тапа (Р5).
- **П3. Без черновика** (Р6). У существующей записи каждый тап — вызов RPC;
  ответ — тактильный отклик и тост «Оплачено €300 · Наличные — Снять» на
  пять секунд. Единственное место, где деньги ждут кнопки, — создание новой
  записи: её ещё нет на сервере, и тап по счёту уходит вместе с «Создать
  запись».
- **П4. Снять оплату** (Р8, Р9). У каждого платежа в блоке действие «Снять»
  и такое же в тосте; платёж исчезает из полученного, запись возвращается в
  остаток/долг. Доступно всем, кто видит запись: владельцу, диспетчеру,
  бригадиру своей команды. В финансах — сторно против той же строки дохода с
  пометкой «Оплата снята: деньги не поступили», в ленте оно не называется
  «Возвратом»; чек аннулируется существующим триггером.
- **П5. Долг** (Р7) = время окончания визита прошло, оплаты нет, инвойса нет;
  висит до оплаты или отмены записи. Статус остаётся «Запланирована» — сама
  запись не становится «выполненной работой» в KPI; в блоке, у клиента, в
  «Должниках», в цвете записи — «Долг €300». Списания нет (Р9).
- **П6. Инвойс** (Р1): режим открывает редактор с предзаполненной записью;
  блок показывает «Инвойс № … · ждёт оплаты до дд.мм»; оплату инвойса сервер
  зачитывает записи сам; визит закрывается по правилу П2.
- **П7. Нет счетов — только «Создать счёт»** (Р2); откат на четыре способа
  убирается. Блок выключен в настройках → закрытие визита фиксирует доход на
  основной счёт команды (отдельный шаг с автозасевом — STORY-067).
- **П8. Возвраты в блоке не показываются** (Р9); RPC возвратов остаются
  владельцу в финансах.

### Состояния блока (вид выбирается глазами, правило 5.1)

1. **Нет команды** — «Сначала выберите команду».
2. **Нет счетов** — пусто + «Создать счёт».
3. **Визит не начался** — режимы «Предоплата» · «Инвойс»; плитки погашены с
   подписью; при уже внесённой предоплате — её строка и остаток.
4. **Визит идёт / прошёл, есть остаток** — сумма остатка (тапабельная) и ряд
   плиток (значок счёта как в финансах; порядок сервера).
5. **Ввод части** — сумма в фокусе, подпись «после оплаты останется €X».
6. **Платежи** — строки «€200 · Наличные · 14:32 · Снять», «€100 · Карта ·
   14:33 · Снять», «Предоплата €50 · Карта», «Инвойс № … · ждёт оплаты до …»;
   при нулевом остатке плиток нет.
7. **Долг** (067) — «Долг €300 · визит прошёл» над плитками.

До первого визуального коммита на iPhone 17 Pro собираются рядом три
варианта с одинаковыми данными, подписанные цифрами: **В1** пилюли `Chip` со
значком в ряд · **В2** квадратные плитки значок-над-именем (сетка
`picker-grid`) · **В3** строки `SettingsRow` с плиткой 28pt; у каждого глиф
нейтральный и цветом счёта; ряд режимов — в тех же трёх вариантах. Экран
сравнения живёт в рабочем дереве и в коммит не уходит.

## User story

Как владелец или бригадир, я хочу одним тапом по счёту зафиксировать
полученные деньги и закрыть визит, предоплату и инвойс выбирать явно, а
ошибочный платёж снять тут же, чтобы деньги лежали на нужном счёте в
финансах, а неоплаченное само стало долгом до момента оплаты.

## Why now

Блок «Оплата» — единственный денежный вход полевого сервиса, и сегодня он
говорит «Без предоплаты», потому что у рабочей команды нет ни одного счёта.
Движок проводок, инвойсов и чеков построен; не хватает двери, которой
пользуются каждый день. Без неё финансы пусты (0 проводок у AirFix).

## Acceptance criteria

1. У команды со счетами блок показывает счета с `show_in_payments = true` в
   порядке сервера со значком и именем; выключенный тумблером счёт исчезает
   при следующем открытии записи.
2. У команды без счетов (Y&D) вместо четырёх способов — «Создать счёт»;
   созданный листом счёт сразу виден в блоке.
3. Визит начался, тап «Наличные» → без дополнительных нажатий запись
   `completed`/`paid`, `payments[]` с одной строкой и `account_id`, тост
   «Оплачено €300 · Наличные — Снять»; в финансах на счёте одна строка
   «Оплата по заявке».
4. Визит не начался: плитки неактивны; режим «Предоплата», 50, счёт → без
   кнопки записано `prepaid_amount = 50`; в финансах «Предоплата по заявке»
   на счёте; в блоке «Предоплата €50 · остаток €250».
5. «Предоплата» на весь остаток → «Оплачено заранее», статус не изменился,
   `payment_status = paid`.
6. Сумма 200 → «Наличные», затем «Карта» на остаток 100 → две строки
   `payments[]` с разными счетами, две строки дохода; `payment_status`:
   `partial` после первой, `paid` после второй; между ними блок показывает
   «Остаток €100».
7. «Снять» у платежа «Карта €100» → в `payments[]` остаётся только
   «Наличные €200», статус `partial`, остаток €100; в финансах на счёте
   «Карта» сторно −100 с пометкой «Оплата снята: деньги не поступили» против
   строки дохода, баланс счёта вернулся; чек по этому доходу аннулирован.
   «Снять» в тосте делает то же.
8. Режим «Инвойс» открывает редактор инвойса с предзаполненной записью; после
   выставления блок показывает номер и «ждёт оплаты до дд.мм»; оплата инвойса
   переводит запись в `paid` (регресс серверной связки).
9. Создание новой записи: тап по счёту откладывается до «Создать запись», после
   создания запись сразу с платежом и проводкой.
10. Без сети тап называет причину («Нет сети — оплата не записана») и ничего
    не теряет молча (`NEVER_PAUSE`, как у всех денежных записей).
11. Подпись блока в Кабинет → «Запись» называет новый смысл; копирайт
    согласован (`babun-copy-keeper`).
12. Чистая логика под тестами bun:test: правило начала визита, расчёт
    остатка и части, валидация (≤ остатка, два знака, счёт выбран), сборка
    вызовов RPC для create-режима; серверные RPC — под pgTAP-подобной
    проверкой SQL-скриптом в 066.
13. `bun run typecheck` = 0, `bun test`, `bun run lint`; скриншоты состояний
    1–6 с iPhone 17 Pro.

## Технический план

### STORY-066 — серверные двери денег (делается первой, 5 SP)

Миграция первым коммитом после schema check; применение к production —
только с явного разрешения владельца (единственная база — боевая).

1. `record_appointment_payment(p_appointment_id uuid, p_account_id uuid,
   p_amount numeric, p_kind text default 'settlement', p_paid_at timestamptz
   default now(), p_request_id uuid)` — security definer; доступ: owner,
   dispatcher, master команды записи; проверяет счёт (`list_payment_accounts_safe`
   тот же фильтр: активен, `show_in_payments`, обслуживает команду), сумму
   (≤ остатка, два знака), дедуп по `p_request_id`; пишет `payments[]`
   (id, method по виду счёта, amount, paid_at, account_id) и зеркала ровно
   как `buildDebtPaidPatch`; `p_kind = 'prepayment'` → `prepaid_amount`;
   `p_close_visit boolean` → `status = completed`; проводки рождает

## Risks

- **Запись по тапу без черновика** — ошибочный тап уже в леджере; защита —
  «Снять» в тосте и у платежа (П4), одна строка дохода и одно сторно на
  ошибку. Принято владельцем осознанно (Р6).
- **Миграция на боевую базу** — единственная база боевая; применяется
  только с разрешения владельца, после schema check, отдельным коммитом;
  функции пишутся по образцу существующих (`record_invoice_payment`,
  `settle_appointment_from_invoice_payment`).
- **Сторно по конкретному платежу** ищет строку дохода по признакам, а не по
  ссылке: `payments[]` и `finance_transactions` не связаны id. RPC записи
  066 кладёт `payment_id` в заметку/колонку проводки, чтобы снятие было по
  ссылке; для старых платежей — по признакам с честной ошибкой при
  неоднозначности.
- **Страница 3232 строки** — блок уезжает в компонент; полный прогон формы
  после врезки.
- **Соседняя сессия** правит цвет записи по состоянию оплаты в основном
  дереве — при слиянии веток «Долг» стыкуется в `record-color.ts` (067).
- **Убираем откат на четыре способа** — без счёта деньги не принять, пока не
  создан счёт (десять секунд листом). Осознанно, Р2.
