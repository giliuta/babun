`/clients/new` и `/clients/[id]` — один файл и одна колонка блоков: первый блок «Клиент» несёт имя, телефон, контакты и **всех** людей карточки строками с ролью, блок «Объекты» показывает под каждой виллой её жильцов строкой-показанием, а заводят жильца там, где его место названо — в листе объекта; единственное действие черновика стоит в футере, у сохранённой карточки действия нет, потому что это контактная база.

## 6. Данные

### Модель
`clients.memberships = [{ group_id, role, location_id? }]` — связь живёт **у члена**. «Люди карточки X» = клиенты, у кого в `memberships` есть X. «Жильцы объекта L» = они же с `location_id = L`. «Чей он сам» = его собственные `memberships`.

**Третий ключ `location_id` — единственная правка модели** (без него «кто живёт в Вилле 5» не имеет ответа). Он вписывается в **ещё не накаченную** `20260921200000_clients_links.sql`, целиком и во всех четырёх местах, иначе срежется молча:
1. триггер пересобирает связь из **трёх** ключей (сегодня `jsonb_build_object('group_id','role')`, строка 84);
2. `location_id` **сверяется с `locations` карточки-группы** (`jsonb_array_elements(g.locations) l where l.value->>'id' = …`); чужой или исчезнувший → `null`, **связь при этом живёт** — человек не перестал быть жильцом Натальи оттого, что виллу стёрли. Эта сверка заодно закрывает то, что стерёг `clients-levels-contract.test.ts:100-113`: третий ключ не свободный текст, контакт им не провезти;
3. дедуп `distinct on (group_id, location_id)` вместо `distinct on (group_id)` (строка 86) — один человек законно жилец двух вилл одной управляющей;
4. домен и мапперы: `ClientMembership` (`local/clients.ts:217-220`), `rowToClient` (`repositories/clients.ts:156-159`), `clientsCached.ts:770,818`, `database.types.ts`.

Белые списки `create_client_with_tags` / `update_client_with_tags` (243, 483) править **не надо** — ключ едет внутри jsonb.

### Когда пишется
- **Черновик** — ровно одна запись в базу по футеру: `create_client_with_tags` со всем черновиком, **включая `memberships`** (связь, пришедшая с дверью, уезжает вместе с клиентом; второго запроса «а теперь привяжи» не бывает). `clientToInsert` уже шлёт непустой массив; триггер `before insert or update of memberships` на INSERT отрабатывает всегда.
- **Связь на карточке** — всегда патч по строке **ЧЛЕНА** (добавили Екатерину к Павлу — правится Екатерина) через `useUpdateClientById` (`queries.ts:446`), которому добавляется `onMutate` с оптимистичной строкой и откат в `onError` (сегодня там только `notify`).
- **Писатель** — новый `use-link-writer.ts` с **картой очередей по `memberId`** (свои `latest`/`pending`/`chain` на каждого). `useJsonArrayWriter` взять нельзя: он однохозяйный (`ownerKey` обнуляет очередь при смене), а тут N чужих массивов.
- **Откуда берётся `prev`** — только из свежей строки члена (`["client", memberId]` или строка источника). **Никогда** из списка мастера: `list_master_clients_safe` / `masterClientJsonToClient` не заполняют `memberships`, и первая же запись оттуда стёрла бы все связи человека. Правило в сторож: если строка приехала окном мастера — блока связей **нет**, а не «есть и пустой».
- **Связь без места дозаполняется местом**, а не дублируется: добавляем жильца, у которого уже есть связь с этой группой без `location_id` — писатель проставляет место в существующей.
- **Инвалидация**: `["client", memberId]` сразу; `["clients"]` — по уходу с поля роли (иначе рефетч перерисует строку и съест автофокус на середине слова).
- `isDirty` черновика (`useClientDraft.ts:144-166`) получает `memberships.length` — сегодня черновик со связью уходит по «Назад» молча.
- `LinkRow` коммитит роль не только по `onEndEditing` (строка 91), но и **на размонтировании** — по образцу `pendingRef` из `ClientExtraContacts.tsx:115-121`.
